# 标签校验处的正则回溯（ReDoS）

## 这一题在教什么

**「慢」可以来自跟数据量无关的地方。**

服务端校验标签格式用的正则长这样：

```
^(\w+\s?)*$
```

看起来挺正常。而它是一条**灾难性回溯**的正则：

| 输入 | 耗时 |
|---|---|
| 16 个 `a` + `!` | 0.003 秒 |
| 20 个 `a` + `!` | 0.048 秒 |
| 24 个 `a` + `!` | 0.771 秒 |
| 26 个 `a` + `!` | 3.14 秒 |

**每多 2 个字符，时间 ×4。** 27 字节的请求让服务端卡 3 秒。

而**同样这条正则**处理 10 万个字符的**正常**输入只要 0.0003 秒。

> 所以这不是"输入太大"的问题。这是**匹配失败时要把指数级的切法全试一遍**。

## 漏洞在哪

`module.py`：

```python
PATTERN = re.compile(r"^(\w+\s?)*$")
...
matched = PATTERN.match(raw) is not None
```

拆开看这条正则：

- `\w+` —— 一到多个字母数字下划线
- `\s?` —— 零到一个空白。**注意它可以"什么都不是"**
- `(...)*` —— 上面这一组重复任意次

问题在"重复"和"可以匹配空"叠在一起：

一个长串 `aaaaaaaa` 拆成几段 `\w+` 的方式有**指数多种**
（第一段取 1 个字符、第二段取 3 个……），
而正则引擎用的是**回溯**算法 —— 它会一种一种试。

## 怎么打通

### 第一步：让它**匹配失败**

匹配成功的时候它不会慢：第一组就把整串吃掉，成功返回。

要让它慢，得让它失败。在尾部放一个 `\w` 和 `\s` 都不认的字符：

```
aaaaaaaaaaaaaaaaaaaaaaaaaa!
```

引擎必须先假设"最后那个 a 属于某个 `\w+`"，试完；
再假设"最后两个 a 属于某个 `\w+`"，再试完；……

**全部试完才敢说不匹配。这是指数级的活。**

### 第二步：盯着耗时看增长

页面上会把这次校验的耗时打出来。从短到长一点点加：

```
16 个 a + !   0.003 秒
20 个 a + !   0.048 秒
24 个 a + !   0.771 秒
26 个 a + !   3.14  秒
```

**每加 2 个字符 ×4** —— 这就是"指数"的样子，而且增长是**可预测**的。
所以真实环境里，40 个字符的输入就是几分钟，50 个就是几小时。

## 为什么这件事跟"输入太大"完全不一样

| | 输入太大的攻击 | ReDoS |
|---|---|---|
| 输入大小 | 很大（几 MB） | **很小**（几十字节） |
| 拦得住吗 | 请求体大小限制能拦 | **任何长度/体积限制都拦不住**（除非你按指数算） |
| 看起来像什么 | 明显异常 | **正常业务请求**（就一个标签列表） |
| 危害方式 | 占带宽、占内存 | 占 **CPU + 线程**，几个并发就打瘫 |

第三行是最要紧的：**它混在正常流量里，WAF 和限流都不一定看得见。**

所以 ReDoS 经常被忽略 —— 大家审的是"输入有没有注入"，
很少有人审"这条正则会不会爆炸"。

## 真实案例

**2019 年 7 月，Cloudflare 全球宕机。**

根因是一条 WAF 规则里的正则：

```
(?:(?:\"|'|\]|\}|\\|\d|(?:nan|infinity|true|false|null|undefined|symbol|math)|\`|\-|\+)+[)]*;?((?:\s|-|~|!|{}|\|\||\+)*.*(?:.*=.*)))
```

这条规则里 `.*.*=` 那一截会灾难性回溯。一条规则，把全世界几百万个网站打掉了几十分钟。

**这件事值得记下来**：WAF 本身也会是故障源，而它的正则没人当"业务代码"来审。

## 怎么修

**一、把这些正则改写掉：别让"匹配一个东西"有多种等价切法。**

| 危险写法 | 安全写法 |
|---|---|
| `^(\w+\s?)*$` | `^\w+(?:\s\w+)*$` |
| `^(a+)+$` | `^a+$` |
| `^(a|a)+$` | `^a+$` |
| `^(a\|ab)+$` | `^(?:ab?)+$` 或者拆成两条 |
| `(\s*)*` | `\s*` |
| `([a-z]+)*` | `[a-z]*` |

规律是：**把可空的部分（`\s?`）拿掉，改成"必须出现的分隔符 + 词"。**
歧义消失了，回溯也就没了。

这一题的安全版就是这个思路：

```
^\w+(?:\s\w+)*$
```

意思是"一个词，然后（一个空格 + 一个词）重复任意次" ——
每个字符属于哪一段是**唯一确定**的，没有多种切法。

**二、给输入设长度上限。**

指数是"长度 ×2 → 时间 ×4"，所以**长度上限的效果是指数级的**：
28 字符上限把最坏情况压到几秒；不设上限的话 40 字符就是几分钟。

这一题靶场设了 28 —— **它是修复的一部分，不是临时措施**。

**三、别用正则做这件事。**

有些校验用代码写反而更清楚，而且没有回溯：

```python
parts = raw.split(" ")
if not all(p.isalnum() or "_" in p for p in parts):
    return "格式不合法"
```

**能不用正则就不用 —— 这是最彻底的"修复"。**

**四、用线性引擎。**

Python 的 `re` 是回溯型的。RE2（`google-re2`）这类基于自动机的引擎是**线性**的 ——
但它不支持反向引用、环视、贪婪/懒惰的细节差异，所以不是所有正则都能搬过去。

**五、给匹配动作设超时（兜底）。**

Python 的 `re` **没有超时参数**。要做得在**外面**包一层：
独立进程或线程池 + 超时，超时就把这次请求掐掉。

这一层不能替代前四条 —— 它只是让你在被打了之后还能活着。

## 怎么系统地找出这一类洞

拿一份正则，一条条看有没有这些形状：

| 形状 | 例子 |
|---|---|
| 量词套量词 | `(a+)+`、`(a*)*`、`([a-z]+)*` |
| 重叠的交替 | `(a\|a)+`、`(a\|ab)+` |
| 可空的分支放在重复里 | `(\w+\s?)*`、`(\s*)*` |

然后用"**一段重复字符 + 一个不匹配的尾部字符**"去打它，
看耗时是不是随长度指数增长。

工具：`redos-checker`、`recheck`、`vuln-regex-detector`、`rxxr2`。

> 一个实用习惯：**把项目里所有正则列一张表**，逐个过一遍。
> 正则通常散落在各处（校验、提取、脱敏、路由、WAF 规则），
> 没人把它们当"需要审计的代码"看 —— 这本身就是它被漏掉的原因。
