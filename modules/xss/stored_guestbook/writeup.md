# 留言板里的存储型 XSS

## 这一题在教什么

**反射型和存储型的区别，不在 payload，在 payload 存在哪。**

| | 反射型 | 存储型 |
|---|---|---|
| payload 在哪 | 你这次请求的 URL 里 | 服务器的数据库里 |
| 触发几次 | 一次（响应里弹完就没了） | **每一次**打开这个页面 |
| 攻击者要做什么 | 诱导受害者点一个特制链接 | 只要受害者打开那个页面 |

同样一句 `<script>`，第二种不需要受害者点任何特别的东西 —— 所以危害大得多。

## 漏洞在哪

`templates/index.html`：

```jinja
<p>{{ m['body'] | safe }}</p>
```

`|safe` 关掉了 Jinja 的自动转义。数据是原样存进数据库、原样渲染出来的。

注意**这不是 SQL 注入**：写入用的是参数化查询（`?` 占位符），存进去的数据是安全的。
问题出在**输出**的时候没有转义。**输入和输出是两回事** —— 后面「怎么修」会展开。

## 怎么打通

**第一步：发一条带标签的留言。**

先在输入框里试试 `<b>粗体</b>`。如果页面上出现了粗体，说明你的输入被当标签解析了。

**第二步：换成能执行代码的。**

```
<script>alert(document.cookie)</script>
```

或者（有些浏览器会拦地址栏/表单里的脚本）：

```
<img src=x onerror=alert(document.cookie)>
```

**第三步，也是最关键的一步：把地址栏清干净再刷新。**

弹窗还会出来。payload 不在 URL 里 —— 它已经在数据库里了。

## 现实里怎么利用

存储型 XSS 的经典打法：

- **留言板 / 评论 / 工单**：管理员后台会看到所有留言 → 打进管理员会话
- **个人简介 / 昵称**：别人打开你的主页就中招
- **文件名 / 导入的 CSV**：渲染列表的时候触发
- **配合 CSRF**：XSS 比 CSRF 强，因为它能读页面内容、能发任意请求

真正有价值的目标是**管理员会看的地方** —— 那里能直接拿到后台权限。

## 怎么修

**输出的时候转义。** 这一题只要把 `|safe` 去掉：

```jinja
<p>{{ m['body'] }}</p>
```

Jinja2 默认会转义，`<` 变成 `&lt;`，浏览器就只会把它当文字。

**但要注意三件事：**

**一、存储型 XSS 的修复必须在"输出侧"做，不能只做在"输入侧"。**

一个很常见的错法是"我在入库的时候把 `<script>` 过滤掉了"。问题是：

- 数据可能从别的入口进来的（API、导入脚本、历史数据）
- 有几十种绕过写法（`<scr<script>ipt>`、编码、大小写、`<svg onload>`）
- 将来某个页面需要原样显示用户内容（比如代码评审），过滤过的数据已经坏了

**正确姿势：入库时存原文，输出时按上下文转义。**

**二、不同的输出上下文，转义规则不一样。**

| 输出到哪 | 需要什么 |
|---|---|
| HTML 正文 | HTML 实体转义（默认行为） |
| 属性值里 | 转义引号 + 实体 |
| `<script>` 里 | JS 字符串转义（不是 HTML 转义！） |
| URL 里 | URL 编码 |
| CSS 里 | CSS 转义 |

用 `|safe` 之前先问一句：我知道这段内容会被渲染到哪个上下文里吗？

**三、真要输出 HTML（比如富文本），用白名单净化。**

```python
import bleach

bleach.clean(user_html, tags=["b", "i", "u", "a"], attributes={"a": ["href"]})
```

不要自己写正则过滤 —— 那是绕过的重灾区。

**配套的纵深防御：**

- `SESSION_COOKIE_HTTPONLY = True`（框架默认开了）—— 让 JS 读不到 session cookie。
  注意它只挡住"偷 cookie"，挡不住 XSS 本身。
- `Content-Security-Policy` —— 能大幅降低危害，但配置容易出错，当补充手段。
