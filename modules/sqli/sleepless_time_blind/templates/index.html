这一题跟 sqli/time_blind 的区别

time_blind 服务端额外注册了一个 sleep() 函数， 于是 payload 跟 MySQL 上写的一样
这一题 没有 —— 数据库本身就没有 SLEEP()， 而且真实环境里 sleep 类函数经常不可用

那延迟从哪来

算点重的东西。延迟不一定要来自"睡"，也可以来自"算"。

想想"慢"还能从哪来：算很多次（循环）、分配很大一块内存、做很多次 IO。 SQLite 里分别对应什么写法？先自己试着让这条查询慢下来。

选哪种原语

循环（递归 CTE）吃 CPU —— 适合，时间稳定、内存不涨
randomblob(N) 大内存吃内存 —— 不适合，换来同样的时间要多花几十倍内存
笛卡尔积自连接吃 CPU，但行数不好精确控制
大表的 COUNT(*)依赖表里有多少行，不稳定

标准：耗时可控、内存和 IO 稳定、重复调用不会把服务打坏。

靶场的上限

靶场给单条语句加了 {{ max_seconds }} 秒的上限。 这不是修复，是为了不让一个请求把 worker 占住几分钟 —— 递归 CTE 的迭代次数是由你的 payload 决定的。

真实目标没有这个保护。所以现实里要小心：一条构造不当的 payload 可能直接把数据库拖垮。造延迟的时候先用小数字校准， 确认量级之后再往上调。
