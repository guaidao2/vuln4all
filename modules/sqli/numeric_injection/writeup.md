# 订单查询处的数字型注入

## 这一题在教什么

**引号不是注入的必要条件。**

前面几道 SQLi 都是**字符型**：你的输入被包在 `'...'` 里，payload 得先用一个
引号把字符串闭合掉：

```sql
SELECT ... WHERE name = '%<你的输入>%'
                        ↑ 得先把这里闭合掉
```

所以很多人形成一句话的结论：**「把用户输入里的引号转义掉就安全了」**。

这一题把这个结论打破。注入点是**数字型**的：

```sql
SELECT ... FROM orders WHERE id = <你的输入>
                                  ↑ 这里没有引号
```

payload 里**一个引号都不需要**：

```
1 OR 1=1
```

## 漏洞在哪

`module.py`：

```python
sql = "SELECT id, owner, item, phone, status FROM orders WHERE id = %s" % typed
```

输入直接落在数字位置。

## 怎么打通

### 第一步：先确认这是个数字位置

```
1        正常返回单号 1
1-0      跟 1 一样     ← 说明输入被当算式求值了
2-1      还是跟 1 一样
```

这三条组合起来就说明：服务端把输入当**算式**算，而不是当字符串比。
**这是个数字位置。**

（页面上会显示服务端实际执行的语句 —— 直接看更清楚。）

### 第二步：不需要引号

```
1 OR 1=1
```

拼出来是：

```sql
SELECT id, owner, item, phone, status FROM orders WHERE id = 1 OR 1=1
```

条件恒真 → 所有订单都出来了，包括别人的。

等价写法（哪个顺手用哪个）：

```
1 OR id>0
0 OR 1=1
1 OR 1
```

注意 `1 OR 1=1 --` 里的 `--` 在这里**没用**（甚至可能弄坏语句）——
因为没有字符串要闭合、也没有后半句要注释掉。

> 这个细节本身值得注意：**payload 的形态取决于注入点的形态。**
> 把字符型的 payload 原样搬到数字型上，经常打不通，而你会以为"这里没洞"。

## 为什么「转义引号」在这里无效

转义引号的逻辑是"把 `'` 变成 `''`（或者 `\'`）"。

可这一题的 payload 里**没有引号**。你把引号处理得再完美，`1 OR 1=1` 照样原样
送进 SQL。

所以正确做法是**参数化**，而不是转义：

```python
con.execute("SELECT ... FROM orders WHERE id = ?", (typed,))
```

**参数化管的是「这是一个值，不是 SQL 语法」这件事** ——
它跟"这个位置是数字还是字符串"**没有关系**。这正是它比转义强的地方：
转义要针对每一种上下文写不同的规则，参数化不用管上下文。

## 真实世界里最常见的组合

很多代码长这样：

```python
# 数字型，裸奔
sql = "SELECT ... WHERE id = " + request.args["id"]

# 字符型，转义了
sql = "SELECT ... WHERE name = '" + escape(request.args["name"]) + "'"
```

第二个位置看起来"做了防护"，第一个位置完全没管。
而开发者的注意力往往全在"我转义了引号"上 —— 因为他脑子里"注入"就是
"引号闭合"。

**这也解释了为什么扫描器比人更容易发现数字型注入**：它会拿 `1-0`、`2-1`
这类算式去探测，而不是只试 `'`。

## 怎么修

**参数化，两种情况用同一个写法：**

```python
# 数字型
con.execute("SELECT ... FROM orders WHERE id = ?", (typed,))

# 字符型
con.execute("SELECT ... WHERE name LIKE ?", ("%" + q + "%",))
```

配套要注意的：

- **不要自己把输入转成 int 再拼**。`int(typed)` 确实能挡掉这一题，
  但它会抛异常、而且换个位置就不适用了。**用参数化，让它成为唯一的手法。**
- **`LIKE` 的 `%` 也要当值传**：`("'%" + q + "%'")` 是错的，
  `("%" + q + "%",)` 才对。
- **动态排序/表名/列名** → 参数化管不到，那里必须白名单
  （去看 `sqli/order_by_injection` 和 `sqli/identifier_injection`）。

## 顺手想想

- 如果代码写的是 `WHERE id = int(typed)`（先转成整数再拼），这一题还能打通吗？
  这样做真的安全吗？（提示：`int()` 抛异常的时候会怎样）
- 如果代码写的是 `WHERE id = '%s'`（数字位置**加了引号**），
  `1 OR 1=1` 还能用吗？那要用什么 payload？
- 为什么说"参数化比转义强"，用一句话说清？
