# 改密码处的二次注入

## 这一题在教什么

**注入点不一定在你直接控制的输入上。**

这一题的注入点是一个**从数据库里读出来的用户名**。而开发者觉得那个东西是可信的：

```
用户输入     = 不可信
数据库里的数据 = 可信
```

**二次注入就是专门打这个错觉的。** 数据一旦进过库，它就被贴上"可信"的标签 ——
而它的来源其实是用户。

## 漏洞在哪

三个功能，两条 SQL 是对的、一条只对了一半：

```python
# 注册：参数化 —— 对的
sql = "INSERT INTO users (username, password) VALUES (?, ?)"

# 登录：参数化 —— 对的
sql = "SELECT username, role FROM users WHERE username = ? AND password = ?"

# 改密码：**只参数化了一半**
stored_username = me["username"]                     # 从库里读出来
sql = "UPDATE users SET password = ? WHERE username = '%s'" % stored_username
con.execute(sql, (new_password,))
#                    ↑ SET 这里是 ?              ↑ WHERE 这里是拼的
```

注意 `SET` 那里**确实**参数化了。开发者知道要参数化 —— 他只是判断错了
"哪一个位置需要"。

## 怎么打通

### 第一步：注册一个用户名带 payload 的账号

```
用户名：admin'--
密码：  随便
```

注册用的是参数化，所以 `admin'--` 就是一个普通字符串存进去了 ——
**这一步本身没有任何问题**。这正是二次注入的特点：第一次接触是安全的。

### 第二步：登录这个账号

登录也是参数化的，所以能正常登录进去。

### 第三步：改密码

改密码时服务端拼出来的是：

```sql
UPDATE users SET password = ? WHERE username = 'admin'--'
```

`--` 把后面的引号注释掉了，于是条件变成：

```sql
WHERE username = 'admin'
```

**它改的是 admin 那一行，不是你自己的。**

### 第四步：用 admin 登录

用 `admin` + 你刚设的那个新密码，就进去了。

页面上会显示每一步拼出来的 SQL —— **对比那三行**，中间那一行就是洞。

## 为什么这类洞特别难发现

| 手段 | 为什么发现不了 |
|---|---|
| **扫描器** | 它给注册接口发 `admin'--` —— 响应完全正常（参数化，存得好好的）。给改密码接口发 `admin'--` —— 也看不出问题（那是个密码字段，被参数化了）。**洞只在"先做 A 再做 B"这个序列里存在。** |
| **人工代码审查** | 你单独看改密码那段：`WHERE username = '<row["username"]>'`。你会觉得没问题，因为 `row` 是数据库读出来的 |
| **静态分析** | 污点分析要么把"来自数据库"当干净（漏报），要么就得跨函数跨请求追踪（误报爆炸） |
| **渗透测试** | 只测单个接口的 payload 是测不出来的，必须**记住自己之前往库里写进去过什么** |

最后一条是渗透测试里很实用的一个习惯：

> **凡是你往系统里写过东西的地方，都记一笔 —— 之后找机会看它被用在了哪。**

## 哪里最容易出现二次注入

一张清单（照着过一遍）：

| 存进去的 | 之后用来干什么 |
|---|---|
| 用户名 | 拼 SQL（这一题：改密码、发消息、加好友） |
| 文件名 / 路径 | 拼读文件的路径 |
| URL / host | 拼跳转、拼抓取目标 |
| 模板片段 | 渲染 → **存储型 SSTI** |
| HTML 片段 | `\|safe` 输出 → **存储型 XSS** |
| 日志字段 | 之后用来检索 |
| 排序偏好 | 拼 `ORDER BY`（那是 `sqli/order_by_injection` 的变体） |

**共同点**：只要有「入库 → 出库 → 再使用」这条链，
就要在那个"再使用"的地方重新问一遍：**它可信吗？**

## 怎么修

**一句话：两处都参数化。**

```python
con.execute(
    "UPDATE users SET password = ? WHERE username = ?",
    (new_password, stored_username),
)
```

背后的原则值得单独记：

> **参数化看的是「这个位置是值还是语法」，跟「这个数据从哪来」没有关系。**

所以"从库里读出来的"东西一样要参数化 —— 因为它最终来自用户。
反过来，一个由服务端自己生成的值（比如自增 id、`uuid4()`）放在**值**的位置上，
参数化也一样是必须的 —— 不是因为那个值可疑，而是因为**参数化是按位置决定的行为，
不是按数据决定的行为**。

配套要注意的：

**一、别用"数据来源"来判断要不要转义。**

这是二次注入的根因。判断的依据只有一个：**这个数据要放进 SQL 的哪个位置？**

```
值的位置       → 参数化
标识符的位置   → 白名单（参数化管不到）
```

**二、标识符也一样。**

如果放进去的不是用户名而是表名/列名，参数化帮不上忙，
那就必须白名单（见 `sqli/identifier_injection`）。
二次注入 + 标识符 的组合更阴险：`ORDER BY '<库里存的值>'`。

**三、注意"部分参数化"。**

这一题是最典型的形态：**一半参数化、一半拼接**。
这种代码看起来非常安全（"我用了 `?` 啊"），所以在审查时最容易划过去。

审查的时候不要看"有没有 `?`"，要看"**有没有哪个片段是拼进去的，它是从哪来的**"。

**四、存储层也可以帮忙。**

`CHECK` 约束、列长度上限、字符集限制 —— 这些不能替代参数化，
但能让"库里的数据"的取值范围小一点，从而缩小二次注入的利用面。

## 顺手想想

- 如果注册时**限制了用户名只能是字母数字**，这一题还能打通吗？
  （提示：那还有别的字段能进库吗）
- 如果改密码那句改成 `WHERE username = ? AND role = 'user'`，
  payload 还是 `admin'--` 吗？要改成什么？
- 为什么说"扫描器发现不了这一题"？如果要写一个能发现它的扫描器，
  你需要额外记录什么状态？
- 这一题的 payload 用了 `--`。如果 SQLite 不支持 `--`（或者被过滤了），
  还有别的写法让那个 `WHERE` 失效吗？
