# 改个数字看别人的订单（IDOR）

## 这一题在教什么

**「认证」和「授权」不是一回事。**

- 认证（Authentication）：你是谁？—— 登录
- 授权（Authorization）：你能看什么？—— 权限检查

新手最容易混的地方是：以为「登录了」就等于「安全了」。这题就是专门打这个误区的。

学名是 IDOR（Insecure Direct Object Reference，不安全的直接对象引用），
听着唬人，其实就是：**URL 里摆着一个对象编号，服务端拿到就用，不检查它归谁。**

## 漏洞在哪

`module.py` 的 `order_detail()`：

```python
rows = fetch("SELECT * FROM orders WHERE id = ?", (order_id,))
```

`WHERE` 条件里只有订单号，**没有 owner**。所以只要有订单号，谁的数据都能查出来。

注意：这一题的 SQL 是**参数化**的，没有注入。参数化只解决「SQL 语法被污染」，
它一点都不能解决「这条数据该不该给你看」—— 这是两件完全不同的事。

## 怎么打通

1. 用 `alice / alice123` 登录。
2. 进「我的订单」，点开一个订单，地址栏大概是 `/order/1001`。
3. 把 `1001` 改成 `1003`。

你会看到 bob 的订单，包括那句「这张卡只发给我们组，别外传」。

## 现实里怎么找这种洞

看到 URL 里有数字 / 有 id，就换一个试试。常见的形态：

```
/order/1001          -> /order/1002
/user/1002           -> /user/1001
/invoice/8871.pdf    -> /invoice/8872.pdf
/api/messages?id=99  -> /api/messages?id=98
{"user_id": 5}       -> {"user_id": 6}
```

不只是数字。GUID、邮箱、文件名、订单号、时间戳，只要是「直接指向某个对象」的标识，
都是候选。

**进阶技巧：** 换成自己另一个账号的 id，对比两个响应，找差别。
或者把 id 换成一个不存在的值，看报错 —— 如果「不存在」和「不是你的」返回不一样，
你就能靠这个差别把别人的数据枚举出来。

## 怎么修

**服务端**必须检查归属，而且要在**每一次**取数据的时候都带上当前用户：

```python
rows = fetch(
    "SELECT * FROM orders WHERE id = ? AND owner = ?",
    (order_id, session["user"]),
)
```

这是最可靠的做法：**把权限条件写进查询本身**，而不是先查出来再在 Python 里
`if row['owner'] != session['user']` 判断 —— 后者很容易在某个分支上漏掉。

再往外一层，通用做法是：

1. **不要用可猜测的连续 ID**（改用 UUID）—— 这只是提高门槛，
   **不能代替权限检查**，因为 UUID 也会泄露。
2. **用间接引用**：给用户看的永远是「他自己的第 3 个订单」这种映射，
   真实 ID 藏在服务端 session 里。
3. **统一错误响应**：「不存在」和「不是你的」都返回同一个 404 ——
   别让攻击者靠响应差别区分。
