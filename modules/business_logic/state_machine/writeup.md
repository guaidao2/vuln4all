# 订单状态机乱序

## 这一题在教什么

**「忘了写一句 if」和「状态模型建错了」是两种不同的问题。**

这一题里每个接口自己的检查**单独看都是对的**：

```python
# 发货
if status != "已付款": reject()
# 退款
if status not in ("已付款", "已发货"): reject()
# 收货
if status != "已发货": reject()
```

三句话都对。但把它们拼起来，能拼出一条**不该存在的路径**：

```
已付款 --发货--> 已发货 --退款--> 已发货 + refunded=1 --收货--> 已完成 + refunded=1
```

**货到了，钱也退了。**

根因不是"漏了一句检查"，而是：

> **「退款」被实现成了订单上的一个布尔字段，而不是状态机里的一个状态。**

而布尔字段可以和任何状态共存 —— 这正是它能溜过所有检查的原因。

## 漏洞在哪

`module.py`：

```python
@app.route("/refund")
def refund():
    if order["status"] not in ("已付款", "已发货"):
        return render(error="这个状态的订单不能退款")

    update("UPDATE orders SET refunded = 1 WHERE order_no = ?")   # ← 只置了标志
    #                    ↑ 没有动 status。订单还停在「已发货」。

@app.route("/confirm")
def confirm():
    if order["status"] != "已发货":
        return render(error="只有「已发货」的订单能确认收货")
    #    ↑ 完全不知道 refunded 这回事
    update("UPDATE orders SET status = '已完成'")
```

`/refund` 之后订单仍然是「已发货」，所以 `/confirm` 的前置检查**顺利通过**。

## 怎么打通

```bash
curl -X POST --data-urlencode 'order=SO-2026-0002' '<发货地址>'
curl -X POST --data-urlencode 'order=SO-2026-0002' '<退款地址>'
curl -X POST --data-urlencode 'order=SO-2026-0002' '<收货地址>'
```

三步，每一步都"合法"。走完之后订单是「已完成」+ `refunded = 1`。

页面上那张状态机图是故意画出来的 —— **请仔细看一遍：「退款」在图上吗？**

## 为什么"旁挂字段"是万恶之源

这个错误有一个很好认的特征：**描述状态的信息散落在多个字段里。**

```
status    = "已发货"     ← 一个状态
refunded  = 1           ← 另一个状态，伪装成标志位
```

于是每加一个接口，你都得记得"要把所有相关的字段都检查一遍"。
而**人一定会忘**。这一题就是忘了一个。

正确的模型只有一条规则：

> **凡是"决定了接下来还能做什么"的东西，都是状态。**

「已退款」决定了"不能收货、不能再退、不能发货" —— 所以它就是一个状态。

把它放进状态机之后：

```
待付款 -> 已付款 -> 已发货 -> 已完成
                      |
                      +-> 已退款（终态）
```

`/confirm` 只要检查「当前状态允许转到已完成吗」，就**天然**把已退款排除了 ——
不需要多加任何一个 `if`。

## 怎么修

**一、转换表是数据，不是散落各处的 if。**

```python
TRANSITIONS = {
    "待付款": ["已付款", "已取消"],
    "已付款": ["已发货", "已退款", "已取消"],
    "已发货": ["已完成", "已退款"],
    "已完成": [],              # 终态
    "已退款": [],              # 终态
    "已取消": [],              # 终态
}

def move(order, target):
    if target not in TRANSITIONS[order.status]:
        reject("不允许从「%s」转到「%s」" % (order.status, target))
    ...
```

好处有两个：

- **新加一个状态时，你改的是"一张表"，不是十个接口**
- 每个接口都走同一句检查 —— 不存在"某个接口忘了检查"这种事

**二、退款金额、库存回滚也跟着状态走。**

这一题里退款**没有回滚库存**。如果回滚了，
`已完成 + 已退款` 这条路径会立刻把库存数变成负数 ——
**对账的时候自然就暴露了**。

> 能自动发现异常的设计，比靠人审查的设计可靠得多。

**三、状态变更要有审计日志。**

每一次转换都记一条：谁、什么时候、从什么状态到什么状态。
这一题的历史面板就是这个意思 —— 真实系统里它还是排查问题的唯一依据。

**四、写测试的时候，测的是"路径"，不是"接口"。**

只测单个接口的边界，是发现不了这一题的。要写的是：

```python
def test_cannot_confirm_after_refund():
    ship(order)
    refund(order)
    confirm(order)                      # ← 这一步应该失败
    assert order.status != "已完成"
```

**把状态机图上所有可能的路都走一遍** —— 包括那些"你不该能走到的"。

## 这一类漏洞怎么系统地找

1. **画状态机**：把所有状态和所有转换列出来，画成一张图
2. **找「旁挂字段」**：除了 `status`，还有哪些字段也描述状态？
   （`paid`、`shipped`、`cancelled`、`refunded`、`locked`、`confirmed`……）
3. **对每一对「状态 + 字段」的组合问**：这个组合**应该**存在吗？
   - `已完成 + refunded=1` → 不应该 → 那它为什么能出现？
   - `已取消 + paid=1` → 不应该 → 同上
4. **数路径**：状态机图上从 A 到 B 有几条路？
   如果有一条你没设计过的路，那就是洞
