# 退款不退货

## 这一题在教什么

**跟"钱"和"状态"有关的接口，都要问三个问题。**

这一题的代码做了一半的事：它检查了订单状态（这一步是对的），
但跳过了另外两件。而**任何一件漏掉，都足以让退款总额超过实付**：

| 要问的问题 | 这一题 |
|---|---|
| 一、这个动作**允许做几次**？ | 没记录 → **能退无限次** |
| 二、金额是**服务端算的**还是客户端说的？ | 客户端给 → **能退 9999** |
| 三、状态**允不允许**这个动作？ | 查了 → 这一半是对的 |

三个问题里做对了一个 —— 而漏洞就在漏掉的那两个里。

## 漏洞在哪

`module.py`：

```python
# 这一半是对的：检查了状态
status = ...
if status not in ("已发货", "已完成"):
    return render(error="这个状态的订单不能退款")

# 洞 1：金额从请求里来。默认值贴心，但那不是校验。
amount = round(float(request.form.get("amount", ORDER_PAID)), 2)

# 洞 2：没有查"这笔订单是不是已经退过了"，也没把结果夹到剩余可退以内。
do_refund(order_no, amount)
```

注意页面上那个输入框**默认值替你填好了** `remaining`。

> **「填好了默认值」和「校验过了」是两回事。**
> 默认值是给用户方便，校验是给服务端安全。
> 把前者当成后者，是最常见的一类想当然。

## 怎么打通

### 绕过一：重复退款（幂等性缺失）

```bash
curl -X POST --data-urlencode 'order=SO-2026-0001' \
     --data-urlencode 'amount=199.00' '<退款地址>'
```

然后把**完全一样**的请求再发一次。余额又加了 199。
退款总额 398 > 实付 199 —— 通关。

### 绕过二：金额由客户端给

```bash
curl -X POST --data-urlencode 'order=SO-2026-0001' \
     --data-urlencode 'amount=9999.00' '<退款地址>'
```

一次就超了。

## 为什么"幂等"这件事必须专门想

「退款」是一个**会产生副作用**的动作。而下面这些情况都会让同一个动作到达两次：

| 情况 | 为什么 |
|---|---|
| 请求超时被重发 | 客户端不知道第一次到底成没成，只能重试 |
| 用户点了两下按钮 | 前端没禁掉，或者网络慢 |
| 前端有自动重试逻辑 | 指数退避重试是标准做法 |
| 消息队列重投 | **至少一次投递**是常态 |
| 网关重试 | 上游超时重试 |

所以"重发一次请求"不是攻击者的专利 —— **正常情况下它就会发生**。

正确做法有两个层次：

**层次一：让动作本身幂等。**

```python
remaining = order.paid - sum_refunds(order_no)
if remaining <= 0:
    return "已经没有可退的金额了"        # 第二次请求被自然挡掉
amount = remaining                       # ← 永远只退"还剩下的"
```

注意这里算的是「**剩余可退**」，不是"该退多少"。
改一个词，整个接口就幂等了 —— 因为第二次调用时 `remaining` 已经是 0。

**层次二：用幂等键去重。**

```python
# 客户端带一个它自己生成的 key，服务端把它跟结果一起存下来
if key in processed:
    return processed[key]                # 同一个 key 直接返回上次的结果
```

金融类接口通常两层都做。

## 跟 `race_condition/coupon_redeem` 的关系

这两道题是同一个洞的两个角度：

| | `refund_logic`（这一题） | `coupon_redeem` |
|---|---|---|
| 两次请求 | **先后**到达 | **同时**到达 |
| 缺什么 | 缺"记下来"这个动作 | 缺"检查和写入之间的原子性" |
| 修法 | 算「剩余可退」/ 幂等键 | 加锁 / 数据库原子操作 |

**修好了一个不代表修好了另一个**：

- 只加幂等键 → 两个请求用不同的 key 并发到达，照样都能过
- 只加锁 → 顺序到达的两次请求都会被放行

## 另外两个常被忘掉的检查

**一、退款要退到原路。**

应当退回到"当初付款用的那个渠道"。否则可以：
把自己的订单，退款到**别人的**账户。

**二、时间窗。**

「超过 30 天不能退」。这一题故意没加，因为时间在靶场里不好演示 ——
但真实系统里这是必须的。测试的时候可以用"改系统时间"或者
"找一笔历史订单"绕过。

## 怎么修（完整版）

```python
def refund(order_no, reason):
    order = load(order_no)                       # 服务端自己加载，不用客户端给的任何值
    refunded = sum_refunds(order_no)              # 已经退了多少

    if order.status not in ("已发货", "已完成"):
        reject("这个状态不能退款")
    remaining = round(order.paid - refunded, 2)
    if remaining <= 0:
        reject("已经没有可退的金额了")

    do_refund(order_no, remaining,                    # ← 金额服务端算
              to=order.pay_channel,                   # ← 退到原路
              idempotency_key=request_key)            # ← 幂等键
```

三个关键点：

1. **金额不接受客户端输入**（连读都不读它是更好的做法）
2. **每次算「剩余可退」而不是「该退多少」** —— 天然幂等
3. **退款是一张流水表**，不是订单上的一个布尔标志

第 3 点值得展开：如果退款只是订单上的 `refunded = 1`，
那你**表达不了**"退了几次、每次多少、退到哪个渠道"。
而这个表达能力一旦缺失，上面所有校验都写不出来。

> 这一点在 `business_logic/state_machine` 那道题里会看到它的另一面：
> 一个布尔字段无法表达状态的**互斥关系**。
