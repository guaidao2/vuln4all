# 下单接口的价格篡改

## 这一题在教什么

**有一整类漏洞不叫「注入」、不叫「越权」，它叫业务逻辑漏洞。**

代码没有违反任何"技术上的安全规则"。这一题的代码甚至**没有任何技术上的错误**：
它正确地读表单、正确地算乘法、正确地把订单写进库。

它只是**相信了不该相信的东西**：客户端传上来的单价。

业务逻辑漏洞的特点：

| | 注入类漏洞 | 业务逻辑漏洞 |
|---|---|---|
| 有现成 payload 吗 | 有 | **没有**，每个系统都不一样 |
| 扫描器能扫出来吗 | 通常能 | **基本不能** —— 请求看起来完全正常 |
| 怎么找 | 看代码里的危险函数 | 看**业务流程**：钱和权限是怎么算的 |
| 修法 | 用安全 API（参数化、转义） | **重新设计流程**，让客户端无权决定关键数值 |

## 漏洞在哪

`module.py`：

```python
unit_price = float(request.form.get("price", list_price))   # ← 单价来自客户端
qty = int(request.form.get("qty", 1))                       # ← 数量也不校验
paid = round(unit_price * qty, 2)
```

而商品目录里明明有真实单价：

```python
CATALOG = {"chair": ("人体工学椅", 1888.00), ...}
```

服务端**手上有正确值，却用了客户端给的值**。

## 怎么打通

### 第一步：看清请求里有什么

正常下一单，用开发者工具的 Network 面板（或者 `curl -i`）看请求体。你会发现：

```
item=chair&price=1888.00&qty=1
```

`price` 是前端展示用的那个单价。**服务端需要客户端告诉它价格吗？**

### 第二步：改单价

```bash
curl -X POST \
     --data-urlencode 'item=chair' \
     --data-urlencode 'price=0.01' \
     --data-urlencode 'qty=1' \
     '<下单地址>'
```

1888 块的椅子卖一分钱。

### 第三步（同一个洞的另一种用法）：数量改成负数

```bash
--data-urlencode 'qty=-5'
```

如果服务端不校验数量，总价会变成负数 —— 那就是"商家倒找你钱"。

## 这一类漏洞怎么系统地找

不要从"技术"入手，从**业务流程**入手。照着这几个问题走：

**一、这个流程里哪些数值决定钱或者权限？**

单价、数量、折扣、余额、积分、运费、税率、返现金额、用户 ID、角色、租户 ID……

**二、那些数值是服务端自己算出来的，还是客户端传上来的？**

这是唯一的关键问题。凡是"客户端传上来、服务端直接用"的，都是一个候选。

**三、如果把顺序打乱呢？**

- 先发货再付款
- 先退款再确认收货
- 先提交订单再用优惠券
- 取消之后还能继续用

**四、如果同一个请求重复发呢？**

这一条单独值得开一道题：`race_condition/coupon_redeem`。

**五、边界值和特殊值呢？**

- `0`、负数、极大值（溢出）
- 小数精度（`0.001` 反复利用舍入误差）
- 空值、重复值、数组（有的框架会把 `a=1&a=2` 解析成数组）

**六、如果"身份"也由客户端给呢？**

这一条最致命 —— 隐藏字段里的 `user_id`、`role`、`tenant_id`。
那已经从"业务逻辑"跨到"越权"了（见 `idor/admin_endpoint`）。

## 真实世界里的同类例子

| 例子 | 说明 |
|---|---|
| 隐藏字段里放价格 / 折扣 / 用户 ID | 这一题 |
| 优惠券叠加 | 两个"互斥"的券同时用，或者同一个券用两次 |
| 整数溢出 | 数量填到让总价溢出成负数 |
| 四舍五入 | 拆成很多笔，每笔都利用舍入误差赚一点点 |
| 退款不退货 | 退款接口只看订单号，不检查"货是否已退回" |
| 免费试用 | 注册-删除-再注册，无限试用 |
| 密码重置不失效 | 用过一次的重置链接还能再用（而且能重复用 → 竞态） |
| 负数量加入购物车 | 凑单凑到负数金额 |
| 导出功能不限制条数 | 一次导出全库 |

## 怎么修

**一、关键数值只能服务端算。**

```python
name, list_price = CATALOG[item]         # 单价只从服务端的数据源取
if not isinstance(qty, int) or qty < 1 or qty > 999:
    abort(400)
paid = round(list_price * qty, 2)
```

**客户端传的 `price` 根本不该出现在代码里** —— 连读都不该读。

**二、把"客户端可以决定什么"写下来，然后逐个审。**

一个实用的做法：给每个接口列一张表：

| 字段 | 谁决定 | 校验 |
|---|---|---|
| `item` | 客户端 | 必须在目录里 |
| `qty` | 客户端 | 1 ~ 999 的整数 |
| `price` | **服务端** | 不接受客户端输入 |
| `discount` | **服务端** | 由优惠券规则算 |

这张表本身就是"设计阶段"的产物 —— 所以这一类也叫 **Insecure Design**（OWASP A04）。
它不是"写错了"，是"想漏了"。

**三、状态机要显式。**

订单状态（待付款 → 已付款 → 已发货 → 已完成）应该用状态机约束，
每个动作都检查"当前状态允许做这个吗"。靠一堆 `if` 散在各处一定会漏。

**四、金额用整数算（分），别用浮点。**

```python
price_cents = 188800          # 单位：分
paid_cents = price_cents * qty
```

浮点的舍入误差本身就是可利用的（拆单赚零头）。

**五、加对账和异常检测。**

技术修不完的时候，这是最后一道防线：
"同一个用户一分钟内下了 200 单，每单都是一分钱" 这种事应该被监控到。
