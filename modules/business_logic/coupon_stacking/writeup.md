# 优惠券叠加

## 这一题在教什么

**每个单独校验都对，缺的是「组合校验」。**

这一题跟 `business_logic/price_tamper` 是两种不同的错法：

| | `price_tamper` | 这一题 |
|---|---|---|
| 错在哪 | 某个**数值**不该由客户端给 | **组合**不该由客户端决定 |
| 例子 | 把单价改成 `0.01` | 把两张合法的券放在一起用 |
| 怎么发现 | "这个数服务端自己不知道吗？" | "这些值**凑在一起**会怎样？" |
| 难度 | 低 —— 改一个数就完事 | **高** —— 每个值都合法，得想到组合 |

第二种更难防，因为你在审代码时看到的是：

```python
for code in codes:
    if code in COUPONS:
        discount += COUPONS[code][1]
```

这段代码**没有任何一行是错的**。错的是它周围**缺了**一段东西。

## 漏洞在哪

`module.py`：

```python
codes = request.form.getlist("coupon")     # ← 一个列表
for code in codes:
    if code in COUPONS:
        applied.append(code)
        discount += COUPONS[code][1]       # ← 每张都减，不查重也不查互斥
```

而页面上白纸黑字写着规则：

> **一次只能用一张券，同一张券不能用两次。**

**规则写在页面上，不等于写在代码里。**

## 怎么打通

购物车是 300.00，券有三张：

| 券号 | 说明 | 减 |
|---|---|---|
| `FULL200` | 满 200 减 50 | 50.00 |
| `NEW30` | 新用户立减 30 | 30.00 |
| `VIP20` | 会员额外减 20 | 20.00 |

### 绕过一：两张不同的券一起用

关键是那个表单字段叫 `coupon`，而 **HTTP 允许同一个名字出现多次**：

```bash
curl -X POST \
     --data-urlencode 'coupon=FULL200' \
     --data-urlencode 'coupon=NEW30' \
     '<下单地址>'
```

服务端把两张都减了：`300 - 50 - 30 = 220.00`。

页面上的下拉框只能选一张 —— 但那只是**界面**的限制，不是协议的限制。
**自己拼请求的时候，界面上有没有那个控件都不重要。**

### 绕过二：同一张券用两次

```bash
curl -X POST \
     --data-urlencode 'coupon=FULL200' \
     --data-urlencode 'coupon=FULL200' \
     '<下单地址>'
```

`300 - 50 - 50 = 200.00`。同一张券被核销了两次。

> 这一条比第一条更值得注意：订单记录里看起来**只有一张券**，
> 所以如果判定写成"用了多张券就算叠加"，这一条会被漏掉。
> 这一题的判定用的是「实付低于基准」—— 那个基准是"只用一张券能到的最低价"。

### 绕过三：三张全上

`FULL200 + NEW30 + VIP20 = 300 - 100 = 200.00`。

真实系统里优惠券通常更多，价格能被压到 0 甚至负数 —— 那就是商家倒找你钱
（跟 `price_tamper` 那道题的"数量填成负数"是同一个后果）。

## 这一类漏洞怎么系统地找

照着这五个问题走，能覆盖大部分：

**一、单个值都合法，组合起来呢？**

- 两张「互斥」的券
- 一个折扣 + 一个满减
- 一张券 + 一次积分抵扣
- 员工折扣 + 活动折扣

**二、同一个东西能提交几次？**

- 同一个参数名在请求里出现多次（这一题）
- 同一个请求重复发送（那是 `race_condition/coupon_redeem` 的角度）
- 用不同的大小写表示同一个东西（`FULL200` vs `full200`）

**三、顺序能换吗？**

先打折再满减，跟先满减再打折，结果不一样。
**如果服务端按"请求里出现的顺序"算，那顺序就由客户端决定了。**

**四、有没有上限？**

- 折扣总额能不能超过商品价格？
- 能不能变成负数？
- 算完之后有没有 `clamp` 回 `[0, 原价]`？

**五、「互斥」是写在文档里的，还是写在代码里的？**

这一题的互斥只写在页面上 —— 那就等于没写。

## 怎么修

**一、先把请求收敛成"一组合法的券"，再算钱。**

```python
ALLOWED_COMBOS = {
    (): 0.0,
    ("FULL200",): 50.0,
    ("NEW30",): 30.0,
    ("VIP20",): 20.0,
}
# 求交集：把请求里出现的券去重、排序，然后当**一组**去查表
picked = tuple(sorted(set(codes)))
if picked not in ALLOWED_COMBOS:
    abort(400, "这组优惠券不能一起使用")
discount = ALLOWED_COMBOS[picked]
```

关键在 `set(...)` 和「查**组合**表」这两步：

- `set` 去重 → 同一张券用两次被消灭
- 查组合表 → 互斥关系变成了**数据**，而不是散落各处的 `if`

**二、算完夹在合法区间里。**

```python
paid = max(0.0, round(GOODS_PRICE - discount, 2))
```

这一句是兜底。即使前面的组合校验漏了，也不会算出负数。

**金额永远要夹**：这是所有跟钱有关的计算的通用规则。

**三、用整数分算钱，别用浮点。**

```python
price_cents = 30000
discount_cents = 5000
paid_cents = max(0, price_cents - discount_cents)
```

浮点的舍入误差本身就能被利用（拆单赚零头），而且对账的时候会折磨你。

**四、核销要落到"券实例"上。**

一个真实的系统里，"券"不是一串代码，而是一条记录：

```
coupon_instance: id, coupon_code, owner, used_at, order_no
```

这样"同一张券不能用两次"就不是靠校验，而是靠**数据库的唯一约束**：

```sql
CREATE UNIQUE INDEX ON coupon_instance (owner, coupon_code) WHERE used_at IS NULL;
```

**用数据结构表达业务规则，比用校验可靠得多。** 校验会漏，约束不会。

**五、把"组合"这件事也当作接口来审。**

给每个下单接口列一张表：

| 输入 | 单独校验 | 组合校验 |
|---|---|---|
| `coupon`（可多个） | 券号存在吗 | **这组能一起用吗** |
| `qty` | 是正整数吗 | **商品数 × 数量 ≤ 库存吗** |
| `points` | 是正整数吗 | **积分 + 券 抵扣后 ≥ 0 吗** |

第三列就是这一题缺的东西。
